# اجرا، فایل و بکاپ

## مسیرهای داده

به‌صورت پیش‌فرض پایگاه داده در `data/db.sqlite3` و فایل‌ها در `data/private-media/` هستند. هر دو از Git خارج‌اند. `DATA_ROOT` و `PRIVATE_MEDIA_ROOT` مسیر مطلق دیگری می‌پذیرند. این محل باید روی دیسک پایدار باشد؛ دیسک موقت یک محیط ابری مناسب این طراحی نیست.

## اجرای محلی

راهنمای README را اجرا کن. `runserver` فقط برای توسعه است. برای اجرای سرویس پشت پروکسی می‌توان از Waitress استفاده کرد:

```powershell
.\.venv\Scripts\python.exe -m waitress --listen=127.0.0.1:8000 config.wsgi:application
```

در تولید: `DJANGO_DEBUG=0`، کلید تصادفی مخصوص محیط، `DJANGO_ALLOWED_HOSTS` شامل دامنه واقعی و `PUBLIC_BASE_URL` برابر نشانی HTTPS سایت تنظیم شوند. فایل تنظیمات محیط در محل امن سرور قرار بگیرد. حساب پیش‌فرض نداریم؛ مدیر با `createsuperuser` ساخته می‌شود.

## پروکسی و HTTPS

سرویس برنامه فقط روی loopback گوش دهد. پروکسی باید هدر `X-Forwarded-Proto` را خودش مقداردهی کند و هدر ورودی غیرقابل اعتماد را عبور ندهد. فقط در این چیدمان `TRUST_PROXY_HTTPS=1` تنظیم شود. سرو مستقیم برنامه بدون پروکسی HTTPS با این تنظیم صحیح نیست.

ابتدا `manage.py collectstatic --noinput` اجرا شود. نمونه اولیه Caddy برای لینوکس، با جایگزینی دامنه و مسیر واقعی:

```caddyfile
example.com {
    request_body {
        max_size 205MB
    }
    handle_path /static/* {
        root * /srv/PerformingArtsCV/staticfiles
        file_server
    }
    handle {
        reverse_proxy 127.0.0.1:8000
    }
}
```

هیچ route یا alias برای پوشه private-media تعریف نشود. فایل‌های خصوصی باید از برنامه و کنترل دسترسی آن عبور کنند. نمونه پروکسی روی سرور واقعی آزمایش نشده است. با تغییر سقف بارگذاری، محدودیت پروکسی و برنامه هماهنگ شوند.

بررسی تنظیمات قبل از استقرار:

```powershell
.\.venv\Scripts\python.exe manage.py check --deploy
```

در تنظیمات تولید فعلی دو هشدار مربوط به HSTS برای تمام زیردامنه‌ها و ثبت در preload انتظار می‌رود؛ این دو گزینه تا تعیین وضعیت HTTPS همه زیردامنه‌ها عمداً فعال نشده‌اند. این هشدارها با خطاهای کلید، DEBUG و کوکی ناامن متفاوت‌اند.

محدودسازی تلاش ورود و ثبت‌نام، محدودیت تعداد اتصال، ایمیل بازیابی رمز، سیاست محتوا و پایش خطا پیش از انتشار عمومی لازم‌اند و هنوز بخشی از این نسخه نیستند.

## سهمیه و تطبیق رسانه خصوصی

سهمیه رایگان پیش‌فرض هر حساب ۱۰۰ مگابایت ده‌دهی (۱۰۰٬۰۰۰٬۰۰۰ بایت) است و مدیر آن را از تنظیمات سایت تغییر می‌دهد. مصرف از اندازه ذخیره‌شده فایل‌های رزومه محاسبه می‌شود؛ لینک HTTP/HTTPS نمونه‌کار فضای فایل مصرف نمی‌کند. سقف پیش‌فرض هر درخواست بارگذاری `MAX_UPLOAD_BYTES=200000000` بایت است؛ چون این حد جریان کل درخواست multipart را می‌شمارد، مقدار آن باید همراه با سربار فرم و محدودیت بدنه پروکسی تنظیم شود. پسوندهای مجاز `.jpg`، `.jpeg`، `.png`، `.webp`، `.mp4` و `.webm` هستند؛ سرور پسوند را با ساختار محتوا تطبیق می‌دهد و به `Content-Type` مرورگر اعتماد نمی‌کند. برای PNG، ساختار chunkها، CRC و جریان فشرده بررسی می‌شود؛ ابعاد تصویر حداکثر ۴۰ میلیون پیکسل و دادهٔ بازشدهٔ PNG حداکثر ۱۰۰ میلیون بایت است. برای JPEG/WebP و MP4/WebM ساختار فریم، ترک و بلوک‌های رسانه بررسی می‌شود تا امضای تنها یا فایل ناقص پذیرفته نشود. آزمون مرورگر پخش یک MP4 واقعی را هم می‌سنجد؛ این کنترل جایگزین رمزگشایی همهٔ قالب‌ها، اسکن بدافزار یا تبدیل رسانه نیست.

فایل‌ها فقط از endpoint مجاز برنامه خوانده می‌شوند؛ پوشهٔ `PRIVATE_MEDIA_ROOT` را مستقیماً از وب‌سرور سرو نکنید. برای بررسی دوره‌ای همخوانی ردیف‌های فایل با دیسک:

```powershell
.\.venv\Scripts\python.exe manage.py audit_portfolio_media
```

فرمان فقط‌خواندنی است: فایل‌های ثبت‌شدهٔ مفقود، فایل‌های بدون رکورد و اختلاف اندازهٔ رکورد/دیسک را گزارش می‌کند؛ در صورت یافتن اختلاف با کد خروج غیرصفر متوقف می‌شود. هیچ فایل یا رکوردی را خودکار حذف یا تغییر نمی‌دهد. برای رسیدگی، ابتدا گزارش را نگه دارید و از پایگاه داده و پوشه رسانه snapshot جداگانه بگیرید؛ فایل‌های ثبت‌شدهٔ مفقود را با تطبیق مالک و نسخهٔ بکاپ بررسی کنید و فایل‌های بدون رکورد را تا تأیید مالک/مسئول داده قرنطینه یا بازیابی کنید. حذف، بازپیوند یا اصلاح اندازه باید پس از بازبینی انسانی، ثبت تصمیم و تأیید بکاپ انجام شود؛ صرفاً orphan بودن دلیل کافی برای حذف نیست. اجرای دوباره فرمان پس از رسیدگی باید بدون اختلاف پایان یابد. هم‌زمانی نوشتن حین audit ممکن است گزارش گذرا ایجاد کند؛ پیش از تصمیم، نتیجه را در پنجرهٔ کم‌ترافیک دوباره بررسی کنید.

## ساخت بکاپ

مراجع نمونه پروکسی: [محدودیت بدنه درخواست در Caddy](https://caddyserver.com/docs/caddyfile/directives/request_body) و [رفتار هدرهای پروکسی](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

برای هر اجرا یک پوشه تازه انتخاب کن:

```powershell
.\.venv\Scripts\python.exe manage.py backup_site backups/snapshot-001
.\.venv\Scripts\python.exe manage.py verify_backup backups/snapshot-001
```

فرمان اول snapshot پایگاه داده SQLite، فایل‌های مورد ارجاع آن و فهرست SHA-256 را ذخیره می‌کند. نوشتن‌های پایگاه داده تا پایان کپی فایل‌ها منتظر می‌مانند؛ برای حجم زیاد، پنجره نگهداری یا روش بکاپ مناسب‌تری لازم است. مسیر موجود بازنویسی نمی‌شود. اگر عملیات قطع شد و manifest ساخته نشد، آن پوشه بکاپ کامل نیست.

فرمان دوم checksum فایل‌ها، یکپارچگی و کلیدهای خارجی SQLite و وجود و اندازه فایل‌های referenced را بررسی می‌کند و داده اصلی را تغییر نمی‌دهد. این فرمان جای آزمون راه‌اندازی سایت از بکاپ را نمی‌گیرد. فهرست checksum هم امضای رمزنگاری‌شده نیست؛ مهاجم دارای امکان تغییر همه فایل‌های بکاپ می‌تواند آن را هم تغییر دهد.

کلیدها و تنظیمات محیط داخل این snapshot نیستند و باید جداگانه محافظت و نگهداری شوند.

## دستگاه دوم و همگام‌سازی

فرمان بکاپ، انتقال به دستگاه دوم را انجام نمی‌دهد. پس از تعیین دو دستگاه، مسیر اتصال و دسترسی، انتقال زمان‌بندی‌شده پوشه‌های کامل snapshot راه‌اندازی می‌شود. انتقال باید روی کانال امن باشد؛ سپس `verify_backup` در مقصد اجرا و شکست آن گزارش شود.

نسخه زنده همگام‌شده برای آماده بودن کپی مفید است، اما حذف و خرابی را هم ممکن است منتقل کند. برای بازیابی، snapshotهای قدیمی مستقل و خارج از محل حفظ شوند. سیاست پیشنهادی شروع، بکاپ روزانه و نگهداری چند نسخه است؛ فاصله دقیق، مدت نگهداری و زمان بازیابی هنوز باید با ظرفیت و نیاز محصول تعیین شوند.

داشتن دو دستگاه به معنی جابه‌جایی خودکار سرویس نیست. failover نیازمند طراحی جدا و آزمون است. مسیرهای کلاینت نباید به آدرس سخت‌افزار خاص وابسته شوند.

## تمرین بازیابی

۱. یک snapshot کامل را در محل جدا با `verify_backup` بررسی کن.
۲. برنامه‌ای جدا با `DATA_ROOT` تازه بساز؛ پایگاه داده و پوشه `private-media` snapshot را به آن منتقل کن. فایل زنده را بازنویسی نکن.
۳. با همان نسخه کد، `manage.py check` را اجرا کن. در صورت تغییر نسخه، مهاجرت را ابتدا در همین کپی آزمایش کن.
۴. مدیر وارد شود، شمار رزومه‌ها و فایل‌ها بررسی و چند تصویر و ویدئو باز شوند.
۵. دسترسی حساب رایگان و مشترک دوباره بررسی شود.
۶. مدت بازیابی و نتیجه ثبت شود؛ فقط پس از این مرحله، تصمیم تغییر سرویس زنده گرفته شود.

نباید پایگاه داده زنده SQLite را با کپی معمولی فایل، مستقل از فایل‌ها، بکاپ گرفت. فرمان snapshot از API بکاپ SQLite استفاده می‌کند.
